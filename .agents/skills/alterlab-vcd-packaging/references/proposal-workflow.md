# 视觉系统提案 → 可编辑工作台

详细阶段顺序、产品使用场景调研、四宫格策划和逐图放行，统一按[进入工作台前工作流](prework-workflow.md)执行。场景图须在研究和母稿/3D明确后生成，不能用“图已加载”替代人物/持物/比例/字形审查。是否制作结构开合图由实际需求和结构依据决定，不能用它凑板块。

本项目的需求入口是 Codex 对话。访谈、网页调研与原创素材创作由 Codex 和当前可用工具执行；导出脚本不会自行搜索网站或调用生图服务。

## 流程与确认点

1. 形成需求确认单，记录已确认事实、尺寸假设和待确认信息。客户资料不充分时先提问。
2. 先由包装 Skill 基于产品和客户信息形成设计假设，再按 [调研来源与选款规则](research-and-selection.md) 定向检索并实际看图；记录日期、来源、候选元素及审美/落地复审结论。不适用则调整检索重新采集，证据不足先补证；合格元素在本案尺寸与文案下做局部小样，复审整体组合后再出选款图。区分经典案例、近期案例、设计概念和实际生产，不把热度等同于适用性。
3. 先交付 A/B 两套盒子 45° 展示图及简短理念/调研依据，采用一致的盒型、比例、背景和相近光线；客户看图选定后深化。仅有文字方向不能视作完成选款。概念展示图若由生图生成，标明其与后续工程的关系；工程必须延续选中方案，差异需明确告知。
4. 先在文件中生成独立图层的草稿工程，以及完整视觉系统的提案数据。这里使用工程数据制作提案中的真实 3D，但暂不打开工作台。
5. 导出设计师报告，保留研究依据、取舍、规则与待确认项；右上角“设计方案”另行生成客户专用单文件HTML，不能复制设计师报告。客户文件只展示左侧设计故事、右侧自动旋转3D、下方九格完整视觉系统，每格有图与理念。故事围绕产品、受众、渠道和有来源的设计转化，不在故事中讲工艺或承诺销量。静态图文必须直接写入HTML，3D失败时仍可阅读。实际检查生成文件后按反馈修订。
6. 设计师明确确认该版本后，使用页面底部的确认入口打开工作台。未确认时不替客户勾选；研发验收时可以对明确标注的演示项目测试此动作。

## 提案数据

完整可运行示例为项目根目录下 `drafts/山间茶-视觉系统.json`。它的 `demo: true` 仅用于通路演示；真实客户项目必须改为 `false` 并填写真实的调研来源。不能沿用演示内容冒充客户调研或设计验证。

在 `drafts/` 保存 `<项目>-提案-v01.json`，核心字段：

- `schema: openbox3d-proposal`、`version: 1`、`id`、`title`、`revision`、`summary`、`brief`。
- `project`：相对于提案 JSON 的 `.boxproj` 路径。工程应有独立的文字、色块、图片和工艺图层。
- `researchRecord`：新项目必须填写图文研究记录JSON的相对路径；导出时调用研究检查。完成搜索不等于完成调研，须保存实际图证、问题结论、采用/淘汰理由与本案转化。
- `customer`：客户专用标题、主张、故事段落、小号来源链接及九个视觉子板块（id/title/body/visuals）。不塞入设计师审核记录；图片由同一工程生成，客户另行提供图片时须内嵌。
- `research`：来源数组，每项填写 `title`、`author`（能核实时）、`url`、`publishedAt`（能核实时）、`accessedAt`、`insight`（观察）和 `application`（本案转化）。只有设计师明确同意跳过研究时，才能用 `researchSkippedReason` 记录原因。
- `palette`：`name`、`value`（六位 HEX）和 `role`。
- `typography`：字体、信息层级、授权情况和字体回退的说明。
- `pending`：仍需设计师或客户确认的事项，不把假设包装为已确认事实。
- `sections`：九个固定主题：`mood`、`context`、`form`、`hero`、`material`、`interaction`、`views`、`light`、`information`。每个主题包含 `title`、`intent`（设计理念）、非空 `rules`（使用规则）、非空 `visuals`，可加 `english` 与 `pending`。
- `fonts`（可选）：每项为 `family`、`weight`（如 `400`、`700` 或变量字体范围 `100 900`）、`src`（授权字体文件相对路径）。字体会内嵌到 HTML 并在交接时传入工作台。没有字体时导出工具会明确提示使用本机回退，不能宣称跨设备字形一致。

视觉条目均须有 `caption`，并按真实内容选择：

- `kind: image`：`src` 是已保存的本地图片路径或内嵌 data URL，`alt` 写清内容。可加 `sourceUrl`。独立保存自己的图像、参考图与生成素材，图注标清类别；概念示意不能标成实拍或真实结构。
- `kind: panel`：`panelId` 指定工程中的盒面，自动从实际图层合成。
- `kind: dieline`：从工程几何和图层绘制展开图。
- `kind: views`：从同一个实际 3D 模型生成正面、侧面、斜侧面取景。
- `kind: palette`：显示本提案色板及用途。
- `kind: finishes`：显示实际工艺图层清单。工艺卡片仅是说明，真实效果看顶部 3D 和实际打样。

九个板块应围绕同一设计，不能把九套各自生成但不一致的包装拼在一起。优先使用真实模型截图、原创设计素材和匹配的场景图。不要为了填满板块，插入与实际盒型矛盾的开箱图。

## 导出与检查

在项目根目录运行：

```text
npm run proposal:export -- drafts/<项目>-提案-v01.json drafts/<项目>-视觉系统-v01.html
```

工具会把 React/three.js、图片、所选本地影棚/地面资源及提供的字体嵌入 HTML。无需 CDN。只允许项目内的素材路径，不会下载外链资源。图片解码、3D 渲染和浏览器显示仍需实际检查，脚本通过不等于视觉验收。

导出只支持当前工作台已有的 7 种参数盒型，盒内尺寸各不超过 600 mm；暂不接收手动节点和线型覆盖，避免已有折叠模型无法对应手工刀版。工程限 500 层，单素材限 12 MB，工程与字体交接数据限约 35 MB。超过限制时说明具体原因，缩减/压缩后再交付。

设计师报告顶部是实际模型，后面为九个板块、字体、调研及版本确认。点击“设计方案”生成另一份客户HTML，嵌入模型、字体和静态截图，查看不依赖工作台。须分别验证报告和按钮实际生成的文件；手机微信本地附件可能限制脚本，不能以桌面HTTP预览冒充微信离线验收。进入编辑仍须本地OpenBox3D运行。

确认前检查所有板块的图片、理念、规则与版式；检查 3D、自动取景和尺寸对应关系。保存评审截图并给直接查看链接。使用 `file://` 被浏览器工具策略阻止时不得绕过；可检查允许的 HTTP 预览，但必须记录“本地双击文件尚未人工验收”，不得声称已经完成该项测试。

## 确认后交接

确认入口会打开一个新工作台窗口，并发送 HTML 内嵌的同一份工程，校验一次性口令、发送窗口和工程 SHA-256。确认信息包含提案名称、版本、时间和原始工程指纹，导出工程时继续保留。

无需设计师自己寻找 `.boxproj`，也不依赖某个草稿恰好已在接收电脑的项目目录里。若本地服务未启动或弹窗被阻止，页面显示连接错误并允许重试。

工作台收到后直接进入设计页：文字可改内容/字体，图片可移动/缩放/裁剪/替换，色块和各类工艺保留独立图层。第一版不提供插画内部路径编辑。原始确认指纹代表载入时的版本；工作台后续修改不自动变成已获客户确认的新版本。

工作台没有新增自动保存功能。关闭、刷新或开发服务热更新前，需导出工程保存修改。视觉确认也不替代结构和印前打样。
